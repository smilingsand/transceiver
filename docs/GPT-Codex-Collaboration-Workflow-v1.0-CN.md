## 开始之前

先完成快速开始，并在 ChatGPT 中成功进行一次真实的只读连接测试。准备好已明确授权的本机项目名称和目录；使用时 Bridge 和 Tunnel 需要运行，当前对话需要启用对应连接器。仅看到本机进程运行或工具列表，并不能证明 ChatGPT 到本机的链路可用。

如果使用 ChatGPT Project，可将 [GPT 协同指令](GPT-Codex-Collaboration-Instructions-CN.md) 的内容复制到目标 Project 的 **Instructions** 中。那份文件是供 ChatGPT 执行的规则，本文是给人看的使用指南。仓库中有文件并不意味着它已自动加载；复制指令也不会启用连接器或授予项目、写入权限。

## 怎样理解这套协作

把 ChatGPT 当作协作的组织者和审阅者：它帮助澄清目标、检查现状、安排工作，并根据实际文件和验证结果审阅交付。本机 Codex 是执行者：它在指定项目和实际权限范围内分析、修改和测试。Bridge 和 Tunnel 是两者之间的通路，不替代判断，也不保证结果正确。

**用户始终掌握目标和授权。** 你可以先要求只读调查，再决定是否允许修改；也可以一开始就明确授权范围内的修改。查看结果、改变方向、决定是否接受，以及批准需要单独授权的操作，都是你的控制点。已经明确授权的工作无需每一步重新批准。

ChatGPT Project、本机 Codex Desktop 的项目列表和 Bridge 的项目授权各自独立：名称相同也不会自动关联或授权。Bridge 的允许目录用于限制项目选择和任务工作目录，并不是操作系统级的完整读取隔离；不要把凭据或不应交给任务的数据放入可访问的上下文。

## 一次典型协作

下面以修复登录问题为例。将方括号内容替换为自己的项目、问题和范围；这些是自然语言提示，不需要手写工具参数。

### 1. 先了解现状

在启用了连接器的 ChatGPT 对话中发送：

```text
请只读检查已授权的 [项目名称]，了解 [登录失败的现象] 可能由什么引起。
先检查项目说明和已有改动，再给我原因、证据和建议方案。
不要修改文件、提交或推送；不确定的地方请说明。
```

ChatGPT 可以直接读取授权项目的文件和 Git 状态；需要深入分析时，也可以交给 Codex 进行只读任务。已有改动应被保护；普通 Git 差异不包含未跟踪文件，必要时需单独检查。读取结果可能截断或超时，不能当作完整证据。

### 2. 决定是否修改

审阅调查结果后，如果同意实施，可继续说：

```text
同意修复 [具体问题]。请在 [允许修改的范围] 内实施，保留已有改动，
运行适当的检查，并说明修改和结果。不要提交或推送。
```

只读授权不等于写入授权。修改还要求当前 Bridge 配置、Codex sandbox 和系统权限都允许写入；你的同意本身不会改变这些设置。如果当前环境只读，任务应报告限制，由你决定如何处理，不能靠提示词绕过。源码默认只读且不允许写入，但实际配置可能不同。源码入口的运行时审批策略不保证弹出交互式批准窗口，因此需要额外授权的操作应事先明确。

提交需要你的明确授权，推送需要单独授权。删除文件、改变安全边界或其他敏感操作也应遵循你的要求和项目规则；授权一项修复不自动包含这些操作。

### 3. 跟进并验收

任务可能需要一段时间。你可以在同一对话中说：

```text
请检查刚才任务的实际状态；如果已结束，核对文件和 Git 差异，
说明做了什么、哪些检查通过或失败、还有什么没有验证。
```

Codex 的报告是线索；文件和 Git 差异显示当前实际改动，测试说明哪些行为得到验证。ChatGPT 应综合这些证据，而不是仅凭执行者报告宣布完成。你可以要求解释、补充检查或调整；确认结果符合需要后再决定下一步。

## 受控 Git 写入

用户授权相应操作后，连接器可直接调用确定性 `git_add`、`git_commit`、`git_push`，无需创建 Codex 任务。服务端各项 `gitWrite` 权限默认均为 false，配置权限本身不代表用户批准。先检查状态和未暂存差异、读取未跟踪文件，再指定路径暂存，审查整个暂存区后提交。提交需要仓库本地身份并拒绝活动 hooks；推送还需精确授权 remote URL/branch，仅支持本地 bare 或无凭据 HTTPS，不支持 SSH、凭据管理器或私有 GitHub 认证推送。参见 [MCP 示例、策略和恢复方法](Git-Write-Tools-BRIDGE-LAB-CN.md)。

## 工作原理与基本概念

你在 ChatGPT 对话里提出目标，ChatGPT 将需要本机处理的指令交给 Bridge，Bridge 安排 Codex 执行并记录状态，最后由 ChatGPT 结合实际结果帮助你验收。并非每次聊天都会启动 Codex；直接查看项目文件也可以不创建 Codex 执行。

| 名称 | 通俗理解 | 例子 |
| --- | --- | --- |
| ChatGPT conversation（对话） | 你与 ChatGPT 的聊天，也是 Bridge 区分工作范围的依据。 | 一个聊天里讨论登录修复，也可能安排多个 Codex Thread。 |
| Task（任务） | 日常语言中的工作或指令；`codex_task` 是提交一轮 Codex 执行的工具。这个词本身不等同于下面任一对象。 | “修好登录”是目标，“检查错误日志”可以是一条指令。 |
| Activity（工作活动） | Bridge 对一个用户意图的跟踪和验收单元，可关联多个 Job 和 Thread。 | 登录修复包含调查、修改和检查；一次执行结束不等于整个目标验收完成。 |
| Job（执行记录） | 一次提交的 Codex 执行及其状态和结果。 | 调查是一项 Job，之后让 Codex 修复是另一项 Job。 |
| Codex Thread（线程／会话） | Codex 连续工作的上下文；多轮指令可以续接同一 Thread。Bridge 的 session 记录用于选择和管理它。 | 调查后续接同一 Thread 修复；独立工作可新建另一个。 |

例如，登录问题的流程可以是：

```text
ChatGPT 对话：提出登录修复目标
    └─ Activity：跟踪整个目标
         ├─ Job 1：在 Thread A 调查 → 查看结果
         ├─ Job 2：续接 Thread A 修复 → 查看差异
         └─ Job 3：需要时在 Thread B 独立检查 → 验收 Activity
```

这是帮助理解的示例，不代表每个目标都需要三个 Job。首次提交时 Bridge 创建 Activity；同一目标仍开放的后续执行或并行工作应复用返回的准确 `activityId`。每个 Job 有 `jobId`，Thread 有 `threadId`；ChatGPT 通常代你保存和使用这些标识。明确续接要求准确 `threadId`，多个线程时尤其不能猜测。每轮还有用于识别请求的 `requestId`：完全相同的调用重试才复用，内容改变则使用新标识。标识及去重受对话范围和状态保留限制，不是永久保证。跨 ChatGPT 对话续接需你明确要求，并提供准确、仍可用的 Thread；不会自动继承整个聊天。

**状态分别看。** Job 可运行、完成、失败、中断或取消；完成只表示该轮执行结束，不证明修改正确或整个 Activity 已验收。Activity 还可能等待后续工作或验证，也可能完成、放弃或取消。查看状态卡或请 ChatGPT 用 `codex_status` 核实实际状态；没有看到新进度不等于卡住。Bridge 保存设置、会话元数据和有界的执行结果，但这不是无限期的完整记忆，文件、Git 和验证结果仍是重要依据。

执行方式也独立于新建或续接 Thread：`foreground` 等待该轮结束或连接结束；`background` 立即返回供后续跟踪；`auto` 在短时间内完成则直接返回，否则转为可跟踪的后台 Job。异步返回只是交出跟踪信息，不代表完成；连接超时也不等于任务停止。异步任务可打开 Activity 卡查看进度。

## 模型、推理等级及会话设置

模型是执行 Codex 指令的语言模型；推理等级是该模型支持的计算强度选择。可用组合、速度、用量和效果会变化，较高等级不保证结果正确。这里讨论的是 **Codex 线程**的设置，不是 ChatGPT 对话中所选模型。

新 Thread 的模型和等级可在本次指令中明确指定；未指定时使用 Bridge 保存的用户默认值，初始默认可来自运营者配置，仍未设置时由 Codex 默认处理。`codex_models` 从当前安装的 Codex 获取可选模型及各自支持的等级，可能使用短时缓存或带警告的旧目录；`codex_settings` 显示已保存默认值、运营者限制和模型目录。请以实际返回为准，不把示例当作固定清单。Bridge 记录或转发的参数不等于已独立证明模型侧执行参数或完整 Token 用量。

在启用连接器的 ChatGPT 对话中，可以直接这样说：

```text
请在已授权的 [项目名称和目录] 新建一个 Codex 线程，只读调查 [问题]。
先核对目录和权限，不修改文件。
```

```text
请继续刚才调查登录问题的那个 Codex 线程，检查 [具体问题]。
先确认准确的线程和工作目录，仍保持只读。
```

```text
请先查看当前可用的 Codex 模型和推理等级，然后在已授权的 [项目] 新建线程，
使用 [模型的准确名称] 和 [支持的推理等级] 执行 [任务]。如果不支持，先告诉我。
```

```text
下一条工作请改用 [模型] 和 [推理等级]：为同一目标新建 Codex 线程，
交接此前的目标、关键发现和未完成事项，再执行 [新指令]。
```

明确新建使用 `sessionMode: new`；明确续接使用 `continue` 和准确 `threadId`。`auto` 仅在当前对话范围内恰有一个近期兼容线程时续接，没有则新建；多个候选时须查状态并选定，唯一候选正忙时须等待或明确新建。省略时采用保存的 `auto` 或 `new` 默认。当前 Bridge 不允许在续接时指定或更改模型和推理等级，也要求工作目录和权限边界兼容；要更换它们就新建线程并交接必要上下文。新线程不会自动获得旧线程的完整历史。

ChatGPT 对话和 Codex Thread 不是同一个会话：同一对话可以有多个 Codex Thread。在 Codex Desktop 点“新会话”也不是在 ChatGPT 中调用 MCP 新建 Thread；Desktop 是否显示外部 Thread、何时刷新取决于环境，不保证自动同步。需要时先通过 Bridge 查询状态。

### 查看和调整默认设置

你可以说：“请打开 Codex Bridge 设置，展示当前默认模型、推理等级、默认项目目录及允许范围。” ChatGPT 可调用 `codex_settings` 打开设置卡；可按界面选择模型及其支持的等级、默认目录、会话行为、访问策略、并发数和完成交接等，然后保存。设置是该 Bridge 实例共享的偏好，不是每个 ChatGPT 账号独立的设置；运营者初始默认和实际硬限制也会显示，保存值仍受限制检查。修改默认值不会改写已有 Thread 的配置。

`defaultCwd` 是省略工作目录时使用的默认目录，必须处于 `allowedRoots` 允许的范围；它不是新增项目授权。允许根目录由运营者配置，设置卡不能扩大它，也不能改变运营者的写入能力上限、审批策略或系统权限。访问策略、任务请求、sandbox 和系统权限共同决定实际可做什么；需要修改安全边界时由有权人员按项目规则处理。ChatGPT 的连接器确认选项控制工具调用确认，并不直接选择 Codex sandbox。

## 长任务和后续工作

长任务可以分成调查、实施和验收等阶段，但无需为每个小步骤新建活动。开始时说明目标、授权项目与修改范围、验收标准和禁止事项；如果只允许调查，就明确只读。让 ChatGPT 保留 Activity、Job 和 Thread 的对应关系，阶段结束时报告已完成、剩余事项、阻塞和实际验证结果。

同一目标的后续工作可续接原线程；需并行时可在同一 Activity 下新建线程，并明确各自负责的文件或使用适当的独立工作区。不同线程可能同时修改同一目录，重叠工作会冲突；同一线程的执行则串行。并发数受当前设置和运营者限制。不要仅因返回慢就重复提交；查询 Activity 卡或状态后再决定下一步。

换线程、换对话或交接给其他人时，提供项目、目标、授权范围、关键决定、已有改动、检查结果、未完成事项和相关标识；不要假定聊天历史自动同步。若只完成一部分，应明确哪些已完成、哪些未验证或失败，不能把执行报告当作验收。根据风险检查文件、Git 差异和适当测试；验证失败时保留证据并安排修正。提交须经用户明确授权，推送须单独授权；不得覆盖已有未提交改动。

请根据任务复杂度和可用预算选择模型、推理等级及并行规模；Token 或用量数据若不可用就报告未知，不要推算成精确账单。任务没有因此获得无限配额，也不保证后台运行一定成功。需要批准或输入时按实际提示和权限处理；输出中的要求本身不会授予权限。

断线、超时或重启后先查询状态和检查可能已有的文件改动，再决定续接或重试。Bridge 重启时未完成的 Job 会标记为中断，已发生的修改不会自动撤销；能否续接 Thread 取决于其后端和实际可用状态，不能保证重启后仍可续接。强制停止可能影响共用执行进程的其他 Job，也不能回滚文件。相同请求的安全重试需在适用范围内复用原请求标识和完全相同的参数；新指令使用新标识。记录和结果受保留范围限制，必要时新建线程并交接已核实的情况。

## 常见问题

| 现象 | 可以怎么做 |
| --- | --- |
| 找不到项目或提示无权访问 | 核对项目名称、真实目录和 Bridge 授权；Desktop 中打开项目并不等于已授权 Bridge。配置更改后，在任务空闲时按快速开始重启受管组件。 |
| 只能读取，不能修改 | 确认你是否明确授权修改，以及当前 Bridge、sandbox 和系统权限是否允许。不要为了完成任务绕过限制；配置问题参见[快速开始](../QuickStart-BRIDGE-LAB-CN.md)。 |
| 本机看似正常，ChatGPT 仍连不上 | 确认对话启用了正确连接器，再检查 Tunnel、组织与工作区关联、权限和本地连接；本机健康不等于端到端连接成功。参见[配置指南](Windows-Setup-BRIDGE-LAB-CN.md)和[控制器参考](Windows-Controller-BRIDGE-LAB-CN.md)。 |
| 等待超时或连接中断 | 不要假定任务已失败或取消，也不要立即重复提交。恢复连接后请 ChatGPT 查询任务实际状态和可能已有的改动，再决定是否重试或停止；停止不能撤销已发生的修改。 |
| Codex Desktop 看不到任务 | 先通过连接器确认任务状态，再检查 Desktop 是否添加了相同的本机目录。历史测试中重启 Desktop 后才显示；实时刷新和其他版本行为没有保证。 |

可以直接复制这段话来恢复情况：

```text
刚才连接中断了。请先检查 [项目名称] 中上一项任务的实际状态和已有改动，
告诉我它是否仍在运行、已完成或失败；确认情况前不要重试或修改文件。
```

任务状态和重试识别有会话及状态保留范围，并非永久记录。Bridge、ChatGPT 和 Desktop 也不会自动共享全部对话历史；重新开始时可能需要你提供目标和关键决定。网络可用性取决于实际环境，不能假定所有任务都禁网。

## 历史记录与限制

原 V1.0 汇总的 T4.1–T5.3 测试曾覆盖只读与受控写入、请求重试、Bridge/Tunnel 启动及单组件恢复、Thread 续接、模型设置覆盖和 Desktop 项目归属。这些是当时环境的观察，不是当前环境的保证；历史原文可查 Git 记录，控制器阶段沿革见 [Windows 控制器参考](Windows-Controller-BRIDGE-LAB-CN.md)。

模型侧实际执行参数的独立证明、完整 Token 统计、Desktop 外部 Thread 实时刷新、真实运行任务的强制断源恢复，以及所有异常保护的动态故障注入，仍未充分证明或解决。历史记录也不能证明当前连接可用；请以本机配置和实际验证为准。需要详细接口与安全边界时，参见 [Bridge Lab 手册](../README-BRIDGE-LAB-CN.md#安全边界)。
